Campus AI — Complete Project Blueprint

Your project should be presented as an NLP-based intelligent campus assistant with an Android mobile application as its user interface. The NLP system is the core of the project; the mobile app makes that intelligence useful to students in their daily college life.

The goal is not to build an ordinary timetable or email app and simply add a chatbot. The goal is to build a system that understands college-related information, classifies it, identifies important dates and changes, and presents the results in a personalized mobile application.

I'll structure this as a comprehensive specification you can give to another AI coding agent, such as a VS Code agent, to implement the project in phases while reusing Person 1's existing NLP work rather than unnecessarily rebuilding it.

1. Project overview

Core: NLP intelligence

Email classification, importance prediction, information extraction, date recognition and timetable-change detection.

Interface: Android application

A student dashboard, categorized emails, timetable, notes, campus map and AI chatbot.

Backend: Python API

Connects the NLP pipeline, database, email integrations, Notion and the Android app.

Storage: PostgreSQL

Stores categorized email metadata, extracted events, user settings, room information and synchronization records.

Project objectives

Automatically classify college emails into meaningful categories.

Predict email importance so students can prioritize what to read.

Extract dates, deadlines, subjects, venues and other useful information.

Identify potential exam, lecture, classroom or timetable changes.

Present college information through a usable Android application.

Allow students to manage their timetable, preferably using Notion as the primary timetable source.

Let students upload notes and ask questions based on their own study material.

Provide an indoor map of the college's single building using actual floor-plan photographs.

Evaluate the NLP system using synthetic data first and real, appropriately authorized test emails later.

Academic emphasis: The project must demonstrate NLP methods, a measurable evaluation, and an end-to-end application that uses the NLP outputs. The other modules support this main goal.

4. Complete functional requirements

Module A — NLP-based smart email management

This is the primary module and should be the first end-to-end feature.

A1. Email ingestion

Accept synthetic emails during development. Later, import emails from a dedicated Gmail test account containing forwarded college emails. Support direct Gmail authorization as a later extension.

A2. Automatic classification

Use Person 1's model to assign categories. Suggested categories include EXAM, ASSIGNMENT, EVENT, DEADLINE, ACADEMIC, ADMINISTRATION, COMMITTEE, JOURNAL, QUERY and TIMETABLE_CHANGE. Reconcile these with the actual model labels before implementation.

A3. Importance prediction

Predict importance using the existing model. Use the model's actual supported levels; MEDIUM is one observed example, not proof that all levels are implemented. Show confidence separately and do not treat confidence as a guaranteed probability of correctness.

A4. Information extraction

Extract relevant dates, times, venues, rooms, subjects, deadlines and event names. Start with explicit date parsing and rules; introduce a dedicated NLP entity extraction model only if required.

A5. Timetable-change detection

Detect language such as “lecture moved to Room 204” or “exam postponed to Friday.” Create a proposed change, show the evidence from the email, and request student confirmation before updating the timetable.

A6. Email search and filtering

Display emails by category, importance, date and unread status. Preserve the original email and link the prediction and extracted information to it.

Example workflow

An email says:

The Computer Networks examination scheduled for 12 November has been moved to Room 204 on 14 November at 10 AM.

The system should:

Store the email and identify duplicate imports.

Predict its category and importance.

Extract the subject, old date, new date, time and room if supported by the text.

Mark the potential timetable change for review.

Show the email, confidence and extracted evidence in Android.

Ask the student to confirm the proposed change.

Update Notion only after confirmation and record the synchronization result.

The example demonstrates the intended behavior. Actual extraction quality must be tested.

Module C — Timetable and Notion synchronization

Notion should be the primary timetable source for students who connect it, while Campus AI provides the mobile interface and intelligent change suggestions.

Required behavior:

Connect a Notion integration with explicit authorization.

Let the user select a timetable database.

Read timetable entries and display them in Android.

Keep a mapping between Notion page IDs and local event records.

Detect updates and refresh the mobile view.

Generate a proposed change from a classified email.

Let the student review and confirm the change.

Update the appropriate Notion entry and record success or failure.

Handle deleted, edited or conflicting entries without silently overwriting changes.

Provide a fallback timetable stored in Campus AI for students who do not use Notion.

Start with reading the Notion timetable. Add write-back only after the read flow works. Notion integrations can only access pages and databases shared with them, and the application must request appropriate authorization.

Module D — Notes library and study chatbot

Students should be able to:

Upload PDFs and supported text-based notes.

Organize notes by subject, semester and custom category.

View and delete their own uploaded files.

Search for notes and retrieve relevant passages.

Ask questions such as “Explain this topic from my Computer Networks notes.”

Receive answers grounded in their uploaded material, with document or page references where available.

Ask general campus-related questions using approved campus information.

Suggested processing pipeline:

Upload → validate → extract text → split into chunks → index → retrieve relevant passages → generate answer with sources

Use a retrieval-augmented generation (RAG) design. Do not pretend the chatbot knows the contents of a document that failed to parse, and do not use one student's private notes to answer another student's query.

Module E — Indoor college map

The college has one building, and floor-plan photographs are available. This means a custom indoor map is a realistic project feature.

Required behavior:

Let students select a floor.

Display that floor's digitized plan.

Support zooming and panning.

Search by room number, room name or location type.

Tap a room to see its details.

Optionally highlight a route along mapped corridors.

Show stairs, lifts, entrances and other navigation points when identifiable from the floor plans.

Allow corrections when room labels are unclear.

Use the actual floor-plan images as source material. Do not invent room numbers or locations. If the source image is unclear, flag the item for manual verification.

For the first version, an image-based custom Android viewer with room overlays is sufficient. Store room metadata and route nodes in PostgreSQL. Live indoor location tracking is out of scope unless additional positioning infrastructure is available.

Module F — Authentication, privacy and notifications

User registration and login.

Per-user access checks on all private records.

Secure storage of OAuth credentials and API keys.

Clear disconnection and data-deletion workflows.

Duplicate-email handling.

Error logging without unnecessarily recording sensitive email content.

Optional local notifications and push notifications for deadlines.

User confirmation for timetable changes and other consequential actions.

For a college demonstration, you may begin with a single test account and a development login. However, the architecture should not assume all students share the same email, notes or timetable.

Database design requirements

Use foreign keys and appropriate indexes.

Enforce uniqueness for provider message IDs within the correct user/connection scope.

Store timestamps consistently and handle time zones.

Use migrations, such as Alembic, instead of modifying production schemas manually.

Keep file binaries in controlled file storage; store file references in PostgreSQL.

Never store OAuth tokens, API keys or passwords in plaintext.

Use a separate prediction record so model upgrades can be evaluated without losing original email data.

Use access controls to ensure that users can retrieve only their own records.

Make sync operations idempotent where possible: retrying should not create duplicate events.

PostgreSQL does not have to store vector embeddings in the first version. If semantic search needs them, pgvector can be added later.
